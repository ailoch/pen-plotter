# SVG-to-Gcode Pen Plotter

Converts an SVG drawing into G-code that drives a Bambu Lab P1S 3D printer as an XY pen plotter.

## Running

[`_Process.py`](_Process.py) is the entry point — prompts for SVG input and gcode output files, then runs:
1. **Parse** SVG → geometry model
2. **Stroke** — generate multi-pass strokes from each shape's stroke width/style
3. **Infill** — add concentric loops to fill interiors of shapes
4. **Drop raw geometry** — remove the now-unneeded parsed centerlines
5. **Route** — reorder paths to minimize travel distance
6. **Generate** — converts intenal geometry model to G-code (lines → G1, arcs → G2/G3)

All logic lives in `lib/`, importable for testing (no module-level side effects).

## Geometry Model

[`lib/geometry.py`](lib/geometry.py): `Segment` (Line/Arc/QuadraticBezier/CubicBezier) → `Path` (list of segments plus a `lineType: LineType`, a subpath) → `PathObject` (list of Path + Style + Transform). `Document` = list of PathObjects. `lineType` (from `lib/settings.py`'s `LineType` enum — `RAW_GEOMETRY`/`STROKE`/`INFILL`/`GAP_INFILL`/`TRAVEL`/bounds-debug values) tags which draw role a subpath belongs to; it lives on `Path` rather than `Style` because a single `PathObject` mixes roles (stroke passes vs. infill loops vs. gap-fill strokes) once stroke/infill generation runs. Defaults to `RAW_GEOMETRY` — the un-stroked, un-filled centerline geometry parsed straight from the SVG, which is a *source* for stroke/fill generation rather than something drawn directly (it has no `heights`/`speeds`/`accels`/`shortTravelThresholds` entry of its own, since nothing should ever emit it as gcode); `tessellate()` carries whatever `lineType` a `Path` has through onto the returned `Path`. `lib/stroke.py`'s `dropRawGeometry` removes every `RAW_GEOMETRY` subpath (and any object left with none) right after stroke+infill generation, before routing ever runs — `lib/plot.py`'s `_addPath` also skips the role defensively, but by construction should never see one.

`Style` also carries stroke info: `strokeWidth`, `strokeColor` (`None` means no stroke — the SVG default), `linejoin`/`linecap`/`miterlimit`, and the dash pair `dasharray`/`dashoffset` (`dasharray = None` means solid). `Style.dashPattern()` returns the SVG-normalized pattern or `None` when the stroke is effectively solid: an odd-length list is repeated to become even (`"5 3 2"` → `5 3 2 5 3 2`, per spec) and an all-zero pattern collapses to `None` (the spec renders it solid). It lives on `Style` rather than in `lib/stroke.py` because `lib/infill.py` needs it too (a dashed stroke doesn't cover the fill's outer band) and `stroke.py` already imports *from* `infill.py` — a helper there would be a circular import. `strokeWidth`/`dasharray`/`dashoffset` are all in the same length space; `PathObject.applyTransformations()` scales all three by `sqrt(|det|)` of the applied transform's 2x2 part (the uniform-scale equivalent — a single width/length can't represent true non-uniform scaling) at the same time it transforms the segments, so they stay correct after the printer-space transform is applied.

Getting the dash lengths into that shared space takes an extra step, because svgelements has **no dash support at all** (no reference to it anywhere in the package) — `stroke-dasharray`/`stroke-dashoffset` only reach `readStyle` as raw strings via the unfiltered `node.values` dict, so all dash parsing is ours. Unlike `stroke_width`, which svgelements resolves into the element's own transformed space (`stroke-width="1"` on a `viewBox="0 0 215.9 243" width="215.9mm"` document comes back as `3.7795` = ×96/25.4, and doubles again under a `scale(2)` group), a hand-parsed dash length starts in raw user units. `readStyle` therefore multiplies both by `sqrt(|det|)` of `values["transform"]` — the **cumulative** chain (root viewport composed with every ancestor group), which is exactly what svgelements applied to `stroke_width`. `values["viewport_transform"]` is the root viewport *alone* and would miss the groups, leaving a dashed shape inside a scaled group with dashes that don't track its own stroke width. Malformed patterns fall back to solid: a value carrying units or a percentage (`"5px"`, `"10%"`) fails `float()`, and a negative dash length invalidates the whole list per spec. A negative `dashoffset` is *valid* though — SVG 2 reads it as shifting the pattern backwards along the path — so it's kept rather than rejected.

Key: `Path.point(t)` spans whole subpath (0 ≤ t ≤ 1), `isClosed()`, `isFillable()` (encloses area, used to gate infill — separate from closed state), `tessellate(tolerance, allowArcs)` reduces to Line/Arc within tolerance, `rotateTo(index)` re-anchors closed paths (for routing). On `Line`/`Arc`: `a @ b` returns their intersection points (any Line/Arc pairing; arc-arc circular only) and `tAtPoint(pt)` maps a point known to lie on the segment back to its parameter (`None` if outside the segment's range) — used together by `lib/plot.py`'s `_splitAtBounds` (see Generate). `segment.subsegment(t0, t1)` returns the piece of that segment over a sub-range of its own parameter, exact on `Line`/`Arc` (a Line interpolates its endpoints, an Arc shifts `t0` and scales `sweep`) — the base `Segment` default raises, since no general formula exists for a bezier's sub-range without re-deriving control points, and every caller (`lib/plot.py`'s `_splitAtBounds`, `lib/stroke.py`'s dash walk) only ever calls it on already-tessellated geometry, which is Line/circular-Arc by construction.

## Key Pipeline Stages

**Parse** ([`lib/svgparse.py`](lib/svgparse.py)): `loadSvg` reads the file into an svgelements tree (raising `SvgParseError` on failure); `parseSvg` then turns it into a `Document` of `PathObject`s — handles groups, paths, rects (including rounded corners), circles/ellipses, lines/polylines/polygons; applies transform stack (flip Y for gcode, offset for pen geometry). `Rect`/`Path`/`SimpleLine`/`Polyline`/`Polygon` are handled by one shared branch in `parseSvgElement`, since all five expose their geometry as the same Move/Line/Arc/QuadraticBezier/CubicBezier/Close segment vocabulary via `segments(transformed=False)` — `transformed=False` because each element's own `transform` attribute is already baked into its geometry by svgelements' structural parser (confirmed: `node.transform` reads back as identity), so re-applying it would double-transform; only the ancestor group chain (`docTransform`) still needs composing into `nodeTransform`. `Circle`/`Ellipse` are deliberately handled separately, not through that shared branch: their `segments()` decomposes the shape into 4 quarter-`Arc`s + a closing `Line`, whereas a single `Arc` (default `sweep=2*pi`) already represents the whole shape exactly in one segment — unifying would trade 1 segment for 5 with no feature gained (unlike `Rect`, there's no `rx`/`ry`-style extra attribute to pick up). `<use>` remains unhandled. Visibility: `display:none` elements are dropped by svgelements before they ever reach `parseSvgElement` (absent from the SVG's own iteration), so nothing needs to be done for that case; `visibility:hidden`/`collapse` is checked explicitly via `_isVisible` (`node.values["visibility"]`, svgelements' resolved-cascade value, same mechanism `readStyle` uses for other presentation attributes). Unlike `display`, `visibility` is inheritable but overridable by a descendant, so `parseSvgElement` always recurses into a `Group` regardless of its own visibility, and only checks `_isVisible` on the leaf branches (shape/text) that actually add something to the `Document`. `_isVisible` also treats element-wide `opacity="0"` (`node.values["opacity"]`) as hidden - true full invisibility, unlike a fractional opacity, which this converter can't represent as partial ink and just draws at full strength regardless of the value; `fill-opacity`/`stroke-opacity` alone are deliberately not checked here since either one being 0 still leaves the other visible. svgelements resolves `opacity` via the same override-wins cascade as `visibility`, which isn't quite true SVG compositing semantics (a real renderer can't let a child "escape" a 0-opacity ancestor group by setting its own opacity back to 1) - close enough for this converter's purposes. If the SVG viewport size doesn't match `canvasSize`, `promptRescale` asks the user how to reconcile it (see Alignment & Scaling below); the drawing is then centered on the canvas. `loadSvg` and `promptRescale` are split out of `parseSvg` so `_Process.py` can run them (file I/O + the interactive prompt) before starting the timer/profiler that measures only the computational parse.

**Stroke** ([`lib/stroke.py`](lib/stroke.py)): For each `PathObject` with a set `style.strokeColor` and `strokeWidth > 0`, offsets every `RAW_GEOMETRY` subpath outward with pyclipper to build a family of concentric `STROKE` passes — structured like `lib/infill.py` (module-level clipper helpers, warn-and-skip on `ClipperException`), and in fact reuses several of them directly (`_SCALE`/`_toClipperPath`/`_appendLoop`/`_drawArcTolerance`/`_joinType`/`_coverageBand`/`_difference`/`_drawResidue`, imported from `lib.infill`). The naive approach (one pass per `fillSpacing`, all offset outward from the centerline) would leave the *centerline itself* unstroked and skew the passes to one side; instead: `numPasses = _passCount(strokeWidth, fillSpacing)` — `ceil(strokeWidth / fillSpacing)`, forced to 1 if `fillSpacing <= 0`, but taken through a near-integer snap first (`math.isclose`, `rel_tol` 1e-9): a width that *is* an exact multiple of the spacing can still divide to `n + 1e-16`, which `ceil` turns into a whole extra pass. That fires both from parse noise (an authored `stroke-width="0.3"` comes back from svgelements' ×96/25.4 space as `0.30000000000000004`, though which side of 0.3 it lands on is a coin flip — `0.29999999999999993` ceils correctly) and from plain division on clean literals (`2.1/0.3` is `7.000000000000001`). The cost isn't just the extra pass: crossing 1→2 also flips the parity, dropping the exact-geometry center pass, so a hairline that should be a single `deepcopy` with its arcs and beziers intact becomes two tessellated offset rings instead — on `tests/comprehensive.svg` that was 25 objects and 862 stroke segments where the snap gives 618 and `s = strokeWidth / numPasses` is the actual pitch between passes (≤ `fillSpacing`). Odd `numPasses` gets a center pass — an exact `copy.deepcopy` of the raw subpath (preserves arcs/beziers exactly; this is the *whole* story for a hairline stroke ≤ `fillSpacing`, keeping a single centerline pass) — plus rings at `k*s` for `k = 1..(numPasses-1)/2`; even `numPasses` has no center pass, with rings at `(k-0.5)*s` for `k = 1..numPasses/2` instead (`_passDeltas`). Either parity lands the outermost ring's `delta + s/2` at exactly `strokeWidth/2`, so the outermost pass's ink reaches the true stroke edge. Each ring offsets a flattened polyline (`tessellate(tolerance, allowArcs=False).vertices()` — closed subpaths omit the duplicate end point, open ones include it, matching pyclipper's `AddPath` expectation) with `MiterLimit = style.miterlimit` and a join type from `style.linejoin` (`miter → JT_MITER`, `round → JT_ROUND`, `bevel → JT_SQUARE`, via `_joinType`); a closed subpath offsets as `ET_CLOSEDLINE`, whose `+delta` Execute yields *both* the outer ring and the inner hole in one call (2 contours per ring), while an open subpath offsets per `style.linecap` (`butt/round/square → ET_OPENBUTT/ET_OPENROUND/ET_OPENSQUARE`), whose `+delta` Execute yields one contour wrapping both sides plus caps. Every resulting contour is appended via the shared `_appendLoop`, tagged `STROKE`. One `PyclipperOffset` per subpath is `Execute`d at each pass delta in turn (the loaded path never changes), and once more at `strokeWidth/2` to get the **stroke band** — the shape SVG would have painted solid, offset with the same join/cap/miterlimit as the passes so their edges line up. The passes tile that band evenly, but at a join sharp enough for `miterlimit` to bevel the spike, each pass gets clipped at a *different* point and they fan apart faster than `fillSpacing`, leaving wedges no pass reaches (likewise inside a curve tighter than `strokeWidth/2`, where the inner offsets collapse). So `generateStroke` ends each object with the same residue check `lib/infill.py`'s `_fillRegion` runs per ring — `band − _coverageBand(all passes, fillSpacing/2)`, handed to the shared `_drawResidue`, which draws each leftover piece's medial axis as open `GAP_INFILL` centerline strokes. Measured on a 30mm V-stroke: at 90° there's no residue at all, at 20°/`strokeWidth=5` the passes leave 0.651mm² across 8 wedges, and at 5° 1.749mm² — all of it inked after the residue pass, with zero extra subpaths generated on the shapes that were already covered. Skipped when `generateGapInfill` is off or `fillSpacing <= 0` (no coverage width to measure against), in which case the stroke output is byte-identical to what it was before this check existed. If pyclipper isn't installed, or `machine.generateStroke` is set `false`, `generateStroke` skips the multi-pass expansion entirely and falls back to a single center-pass `deepcopy` per stroked subpath (the pre-multi-pass centerline-only look) - the missing-pyclipper case additionally warns once. Must run before `generateInfill`, since a stroked object's fill inset depends on `strokeWidth`/`linejoin` (see below).

**Dashes**: if `style.dashPattern()` is non-`None`, every `RAW_GEOMETRY` subpath is split into its inked pieces by `_applyDash` *before* anything above runs — so the passes, band, residue and even the no-pyclipper fallback all operate on dashes rather than the whole outline. The split works on the **tessellated** path (`tessellate(tolerance, allowArcs=True)`, which by construction holds only Lines and *circular* Arcs): arc length is then linear in `t` for every segment, so the walk is exact arithmetic and `geometry.py`'s `subsegment` (shared with `lib/plot.py`'s `_splitAtBounds`) restricts each piece exactly. Dashing the raw beziers instead would need a numerical arc-length inversion per split. `_dashSpans` turns the pattern into inked `[start, end]` arc-length spans — a positive `dashoffset` shifts the pattern forward, and SVG 2's backwards shift for a negative one falls out of Python's `%` returning a non-negative result. Spans that touch end-to-end (a zero-length "off" entry like `"5 0"`) are merged so the router sees one dash, not two meeting at a point. On a **closed** path whose walk is "on" across the start point, the last dash is stitched onto the front of the first: SVG joins there rather than capping twice. The dashed subpaths are new `Path`s held in a local list, so `obj.geometry`'s `RAW_GEOMETRY` entries stay whole and `generateInfill` still sees the undashed outline it needs. Zero-length dashes are dropped, so round-cap dotted patterns (`"0 4"`) aren't supported yet.

**One-sided dashes**: a dashed stroke over a fill splits its band at the centerline. The inner half is territory the fill has to cover continuously anyway (SVG paints fill straight across the dash gaps), and only the outer half is where a gap is meant to show bare paper — so each half is drawn exactly once. `generateStroke` skips the center pass and per-delta rings entirely, and instead diffs the dash band against the object's fill region (`_resolveFillRegion`, shared with `lib/infill.py`) and hands the outward remainder to `_fillRegion` with `firstDelta = penWidth/2`, tagged `STROKE` — reusing the fill's own concentric-rings-plus-residue tiling so the outward half inherits its coverage guarantee. Rings inset from *every* boundary of that region, including the centerline cut the difference made, so the two halves abut there with no seam. `generateInfill`'s matching half of the deal is excluding a dashed stroke from its `hasStroke` inset (see Infill). Only applied when the fill will actually be drawn — no fill region, `fillSpacing <= 0`, or a `ClipperException` resolving the region all fall back to normal two-sided dashes, since nothing else would cover the inner half.

**Infill** ([`lib/infill.py`](lib/infill.py)): For each fillable `PathObject`, use pyclipper to resolve the fill region respecting `fill-rule` (`nonzero`/`evenodd`), then fill it by **tiling concentric rings inward and, at every ring, drawing centerline strokes over whatever that ring's ink misses** (`_fillRegion`) — so coverage is complete *by construction* rather than relying on a global post-pass. Gated on `lineType == RAW_GEOMETRY` (so a previous pass's own generated loops are never re-used as a fill source) plus `isFillable()` (encloses area, computed via shoelace formula - summing the *absolute value* of each shoelace term rather than taking the absolute value of their sum, so a self-intersecting path with opposite-wound lobes, e.g. a bowtie/figure-eight, can't cancel to zero and read as unfillable; this makes `isFillable()` a deliberately permissive gate, since the actual fill-rule-aware geometry is resolved afterward by pyclipper, which correctly reduces a truly zero-area path back down to nothing), not `isClosed()`.

The tiling: insets are measured from the resolved region boundary, and ring `k`'s centerline sits at `firstDelta + k*spacing`, inking the band `[center - spacing/2, center + spacing/2]`. `firstDelta` is `penWidth/2` (so the ring's *real* ink edge - not the more conservative `spacing/2` the interior tiling assumes - lands exactly on the region boundary, the pen's outer edge lining up with the SVG shape edge) or `strokeWidth/2 + penWidth/2` for a stroked object (the outer `strokeWidth/2` is inked by the stroke passes instead). Using `penWidth` rather than `spacing` here is deliberate: `spacing` is set conservatively so interior gap-detection stays safe even against a thin/worn pen, but that same conservatism at the outer edge would leave the boundary looking under-filled - a visible white sliver - rather than landing exactly on the shape's true edge. A **dashed** stroke is deliberately excluded from that inset (`hasStroke` also requires `dashPattern() is None`): it only inks part of the outer band, so insetting past it would leave an uninked notch in every dash gap — territory SVG paints solid. A dashed object therefore tiles from its raw centerline, and `lib/stroke.py` draws only the outward half of each dash so the two meet there without overlapping (see Stroke). All offsets come from a single `PyclipperOffset` loaded once and `Execute`d at growing deltas — erosion composes, so this can't compound discretization drift; a stroked object's ring offsets use the stroke's own `linejoin` (`_joinType`, shared with `lib/stroke.py`) so the fill hugs the stroke's inner edge at corners, else `JT_ROUND`. Each ring's loops are re-fit with `fitLines=True` to recover circular arcs and tagged `INFILL` via `_appendLoop`.

The per-ring residue (`_drawResidue`, on by default via `processing.generateGapInfill`) is the part of ring `k`'s annulus `[Execute(-(center-spacing/2)), Execute(-(center+spacing/2))]` that the ring's own ink doesn't cover — the acute-corner wedges and, crucially, the *dropped thin features* (a stem or crossbar narrower than `spacing`, where the inset leaves no closed loop at all, so the outline "vanishes"). Successive annuli abut exactly (`annulusInner_k == annulusOuter_{k+1}`), tiling the whole region seam-free; when a ring comes back empty but its shallow boundary is still non-empty (a region thinner than `spacing` end-to-end, e.g. a sliver-only shape), that whole core is residue. Residue = `annulusOuter − annulusInner − coverage`, where coverage is the ring's ink band (`_coverageBand`: the loops offset as `ET_CLOSEDLINE` by `spacing/2`, the true ±`spacing/2` sweep around the loop curve). Clean it (`_offsetPolys` morphological open at `tolerance/2` plus an `(spacing/2)²` min-area threshold — which also discards the benign sub-`penWidth` specks between adjacent rings, since `fillSpacing` is deliberately set under the real pen width so those are inked anyway), group each surviving piece with its holes via an `Execute2` PolyTree (`_polyTreeGroups`, so an annular residue stays whole), then (`_drawResidue` is shared with `lib/stroke.py`, which runs the same check over a whole stroke band rather than one ring's annulus — see Stroke above):

- **thin piece** (the common case, ≤`spacing` wide so it survives *no* `spacing/2` erosion): draw its **medial axis** as open `GAP_INFILL` centerline strokes (`_medialAxisLines` → `_appendLine`). A pen tracing the skeleton with ±`spacing/2` ink covers a region of half-width ≤`spacing/2` completely, so a plain sliver becomes a single line and a Y-shaped piece becomes ~three — replacing the old approach's disconnected double-passed loops. The skeleton is approximated by a `scipy.spatial.Voronoi` of the piece's densely-resampled boundary (edges capped at `spacing/_MEDIAL_SAMPLE_DIVISOR`, currently `spacing/6`; sampling *too coarsely* costs more than it saves — the skeleton comes back jittery, which loses coverage and defeats the arc fitter, so it emits many short segments instead of a few long arcs: at `/4` horse.svg's gap fill needed 2688 segments and 242KB of gcode, at `/6` just 495 segments and 134KB for the same ink), keeping only Voronoi ridges whose both endpoints lie strictly inside the piece (`pyclipper.PointInPolygon`, bbox-gated first so near-infinite Voronoi vertices from boundary sites don't overflow clipper's 64-bit ints), then turning that graph into strokes. Two steps keep the stroke count sane, since a Voronoi skeleton of a densely-resampled boundary sheds a lot of tiny ridges around every corner and junction: **spur pruning** drops each leaf branch (tip → first branch point) shorter than `spacing/2`, which lays down no ink the branch point's own ±`spacing/2` disc doesn't already cover — a walk ending on another tip is a standalone component, not a spur, so it's kept; and the **decomposition carries on through junctions**, taking whichever unused branch best continues the current heading rather than ending a stroke at every branch point, so a continuous spine stays one stroke (every edge is still drawn exactly once). Ending at junctions instead fragmented one spine into many sub-pen-width subpaths, each costing its own pen lift and inflating the item count `lib/route.py`'s O(n²)-per-sweep 2-opt has to sort — on `testDrawing.svg` that was 742 gap-fill subpaths (median 0.097mm, a third of a pen width) and 2.2s of routing, vs 235 (median 0.304mm) and 0.66s after, at byte-identical coverage. Numeric-noise fragments shorter than `tolerance` are still dropped at the end.
- **wide piece** (survives a `spacing/2` erosion — a genuinely broad gap, rare): fall back to concentric loops (`_fillGap`, tagged `GAP_INFILL`), whose first inset halves from `spacing/2` down toward `tolerance/2` so even a piece only slightly wider than `spacing` yields a loop. Also the fallback when `scipy`/`numpy` is unavailable or the Voronoi degenerates.

Overcoverage is acceptable (a doubled pen pass is invisible on paper) — the invariant is that `R_k ⊆ ink(ring) ∪ ink(residue) ∪ R_next`, so nothing is left uninked. Interior coverage width (ring pitch, residue detection, gap-fill half-widths) is always `fillSpacing`, never `processing.penWidth` - `firstDelta` is the one exception, since it places a boundary the pen's real ink has to reach exactly, rather than measuring interior coverage. When `generateGapInfill` is off, rings still tile but residue is skipped. `firstDelta`'s `strokeWidth/2` gap means an unstroked fill-only shape tiles from its raw boundary; a stroked one tiles from the stroke's inner ink edge, abutting the stroke band by the same invariant (no cross-object coverage bookkeeping needed anymore).

**Route** ([`lib/route.py`](lib/route.py)): TSP-like optimization (nearest-neighbor + 2-opt + anchor-optimization + rendezvous move) to reorder objects and choose entry points, minimizing pen travel. Two-pass: order internal subpaths within each multi-subpath object, then order objects themselves. Travel cost isn't pure XY distance: `_travelCost` adds an estimated pen lift/lower time (converted to equivalent XY distance at travel speed, so it stays additive with the distance term), mirroring the real pen-up move `lib/plot.py` will later emit - prevMoveHeight → travelHeight on lift, then travelHeight → nextMoveHeight on lower, at `min(speeds[travel], maxVerticalSpeed)` since a printer's Z axis is typically slower than X/Y. No penalty is added when the travel is under `shortTravelThresholds` (the smaller of the departure/arrival roles', same rule `plot.py` uses to decide the pen never lifts at all). A subpath item's role is its single `lineType`; a whole-object item takes its first/last subpath's `lineType` (`_itemLineTypeStart`/`_itemLineTypeEnd`), which can differ when the object mixes roles - `startRole`/`endRole` swap with `rev` the same way `startPt`/`endPt` do. By the time routing runs, `dropRawGeometry` has already removed every `RAW_GEOMETRY` subpath (see Geometry Model), so every item these helpers see has a real drawn role with a `shortTravelThresholds`/`heights` entry.

**Generate** ([`lib/plot.py`](lib/plot.py)): For each path, tessellate to Line/Arc, emit G1/G2/G3. `_addPath` skips a `RAW_GEOMETRY` path defensively if one somehow reaches this stage (it shouldn't - `dropRawGeometry` removes them all beforehand). Every tessellated Line/Arc is first run through `_splitAtBounds(segment, bounds)` against the canvas rect in nozzle space (`_canvasBoundsNozzle` - `canvasOffset - penOffset`, since segment coordinates are always nozzle space regardless of `visualization.showPenPos`, which only affects preview labeling): a cheap bbox check short-circuits the common fully-in/fully-out cases, and for a segment straddling the edge, the crossings are computed algebraically — the segment is intersected with each of the rect's 4 edges via the `@` operator (`Line`/`Arc.__matmul__` in `lib/geometry.py`: line-line via 2D cross product; line-arc by inverse-mapping the line into the arc's circle space, where it becomes a quadratic in the line's own t, which the affine map preserves — handling elliptical arcs for free; arc-arc via the two-circle construction, circular only) and each hit mapped back to the segment's own parameter with `tAtPoint`. Endpoint grazes, corner double-hits, and tangency double-roots are collapsed (`_BOUNDS_T_EPS`), pieces are classified by midpoint with same-side neighbors merged, and consecutive in/out runs are built via `segment.subsegment` (exact for both Line and Arc, since Arc's `t0`/`sweep` restrict cleanly to a sub-range). Each resulting piece is either drawn under its original `lineType` (in bounds), dropped silently (`processing.showOutOfBounds = false`, the default - the next surviving piece's leading travel move naturally bridges the gap), or drawn under `LineType.INVALID` (`showOutOfBounds = true`, for spotting problem areas in the slicer preview without physically cropping anything). Each object that loses at least one piece this way (in either mode) has its `id` appended to `createFile`'s `outOfBoundsNames` list (`_addPath`'s `droppedThisObject` flag caps it at one append per object); once the whole document is written, a single warning naming every such object is printed — "cropped" or "marked as invalid" depending on `showOutOfBounds` — mirroring `parseSvg`'s one-line-per-run text-dropped warning rather than printing per-segment. Intersperse travel moves (short = pen-down, long = pen-up). Each path's `lineType` drives which height/speed/accel and slicer feature label is used for its draw moves (and for the short-travel move immediately before them). Cosmetic: alternate +0.001mm Z per object for preview layering. `visualization.style == "segment"` cycles `segmentTypes` once per drawn segment (`_nextSegmentType`) with no notion of shape closure - so a closed path whose segment count doesn't divide evenly into `len(segmentTypes)` would otherwise wrap its last segment back onto the same color as its first, which visually merges them since they're adjacent (the loop's closing junction). `_addPath` predicts this before drawing a closed path's segments (`firstSegColor`), and `_skipRepeatedClosingColor` pre-advances `_DrawState.lastMoveType` right before the real last-segment draw call if the collision would occur - landing one color further out instead of repeating the first (a 4-segment loop over 3 colors becomes a-b-c-b, not a-b-c-a). No gcode is written for the synthetic pre-tick; it only shifts where the real draw call's own cycling starts from. The prefix/suffix gcode templates are copied through `_fileAppend`, which substitutes `{...}` blocks: each block's contents are an arithmetic expression evaluated against the `replace` namespace — `TRAVEL_HEIGHT`/`TRAVEL_SPEED`/`TRAVEL_ACCEL`/`LINE_WIDTH`/`END_X`/`END_Y` (raw floats) plus the string-valued `EXTRUDER_OFFSET`/`BED_EXCLUDE_AREA`/`WAIT_FOR_PEN`. So `{TRAVEL_SPEED/2}` or `{TRAVEL_HEIGHT + 10}` work, not just a bare `{TRAVEL_SPEED}`; numeric results are formatted via `_fmtNum`, strings pass through when referenced bare. Evaluation is **not** `eval` — it's an AST whitelist (`_evalTemplateNode`) that permits only names (looked up in `replace`), numeric literals, and `+ - * / // %` (with operands required numeric via `_requireNumber`). Deliberately excluded: attribute access, calls, subscripts, and `**`. This matters because a prefix/suffix template can arrive alongside a shared/downloaded config, and `eval` — even with `__builtins__` stripped — is escapable to arbitrary code via attribute traversal from any object literal (`().__class__.__bases__[0].__subclasses__()`); the numeric-operand rule also blocks the `'x'*999999999` / `2**999999999` resource-exhaustion vectors. A block that fails to evaluate (unknown name, bad syntax, arithmetic on a string, or any disallowed construct) is left in place verbatim with a warning, preserving the old leave-unrecognized-keys-as-is behavior.

`WAIT_FOR_PEN` is the multi-line block both prefix templates use for the pause that lets the user load a pen (it replaced a bare `G4 S{LOAD_DELAY}`, and `LOAD_DELAY` is gone from the namespace with it — these two templates are the only ones there are). `_waitForPen` takes the whole `Settings` rather than the fields it currently needs, so later additions to how the delay is configured don't touch the call site. With `motion.showLoadProgress` (the default) the dwell is split into steps with an `M73 P` between each, counting **100 → 0** as the fraction of the wait *remaining* (`P` is normally progress, but what the user is reading here is a countdown), which also leaves the printer sitting at "0% done" as the drawing starts since nothing else in the pipeline emits `M73` yet; with it off, it's the single silent dwell it always was. Either way it emits `G4 P` (milliseconds) rather than `G4 S` (seconds), `P` being the more widely supported of the two.

The step size is the 500ms tick expressed as a percentage and then **clamped into 1%–5%**: at most 5% so a short delay still counts down smoothly, at least 1% because below that the extra `M73`s only redisplay the number already on screen. Clamping the step (rather than emitting sub-1% ticks and merging duplicate percentages afterwards) keeps every step uniform and bounds the block to 20–100 steps for any delay — 400s comes out as exactly the 101 whole percentages, 4s apart. The remaining subtlety is that step boundaries are taken from the **cumulative** time (`round(delayMs * i / steps)`), so rounding each dwell to whole milliseconds can't accumulate into a drift that changes how long the wait actually lasts.

## Tessellation (`Path.tessellate`)

Bidirectional greedy fitter: reduces any curve to Line/Arc within tolerance, working in normalized subpath-space (0 ≤ t ≤ 1) so fits can span segment boundaries. Key behaviors:
- **Already-final segments atomic**: `Line` passthrough (unless `fitLines=True`), circular `Arc` passthrough → prformance gain.
- **Line merging**: `appendMerging` catches exact-collinear runs the fitter misses (each already fits individually).
- **`fitLines=True`** (used by infill arc-recovery): re-fits raw polygon points → arcs, with optimized fast path for all-`Line` ranges (no per-segment interior sampling).
- **Numerically unstable circumcircles rejected** via `MAX_RADIUS_TO_CHORD` guard — filters near-collinear noise.
- **`allowArcs=False`** skips the fitter entirely and flattens each segment independently via `Segment.toPoints` (base-class recursive subdivision; `Line`/`Arc` override it with an exact split). `toPoints` checks flatness at two interior points (1/3, 2/3) per recursion level, not just the midpoint — a single midpoint sample can land exactly back on the chord for a point-symmetric curve (e.g. an S-shaped cubic bezier whose inflection sits exactly at t=0.5), which would wrongly read as "flat" and collapse the whole curve to a straight line even though it bows out on both sides of that point.

## Error Handling

**Missing/invalid config file** — `Settings.initFromJson` catches a missing file (`FileNotFoundError`) and parse errors (JSON syntax, type mismatches) separately, prints a clean one-line error message (e.g., `No terminal defined for 'f' at line 21 col 1`), and proceeds with defaults either way. The program continues so the user can still test with the default settings if needed.

**Invalid SVG file** — `loadSvg` wraps `svgelements` and re-raises any parse error as `SvgParseError`; it also raises `SvgParseError` itself if the parsed SVG has no `viewBox` (this converter needs one to size the drawing — `svg.viewbox` is otherwise `None`, which `promptRescale`/`parseSvg` each re-assert non-`None` since that narrowing doesn't cross function boundaries), or if the `viewBox` has a non-positive width/height (`svgelements` stores negative values as-is rather than rejecting them, which would otherwise silently corrupt the transform math in `parseSvg`). `_Process.py`'s `run()` catches `SvgParseError` around just the `loadSvg` call, prints it, and returns `RunResult.BAD_INPUT`; the main loop re-prompts for a new input file on that result, clears the cached `document`, and retries. No config reload needed.

**Empty/degenerate paths** — a `<path>` with no drawable segments (e.g. `d=""`, or only `Move` commands) is dropped in `parseSvgElement` rather than added to the `Document` with a placeholder empty `Path`: nothing to draw means nothing to route, and `PathObject.start()`/`end()` (used by `route.py`'s ordering) assume at least one segment.

**Output retries & the cached document** — `run()` parses/infills/routes once and caches the resulting `document` in a module global. A write failure (`createFile` returns `False` → `RunResult.BAD_OUTPUT`, e.g. the target gcode is open in another program) re-prompts only for the output file and redoes just `createFile` against the cached `document` — it does not re-parse or re-ask the rescale question. The cache is cleared only when the input file changes (`BAD_INPUT`). The rescale prompt and SVG load run before the timer/profiler starts, so neither the reported time nor the profile includes user think-time.

**Output file safety** — `lib/plot.py`'s `createFile` writes to a temp file in the output directory and only `os.replace()`s it over the real target on full success. If anything fails mid-pipeline (missing settings keys, missing prefix/suffix gcode files, etc.), the output file is left untouched — can't be truncated by a partial crash.

## Settings (`lib/settings.py`, `config/bambu_p1s_config.json`)

`Settings` (a dataclass, in `lib/settings.py` alongside the `LineType` enum it keys heights/speeds/accels/lineTypes by) is shared across the whole pipeline — `parseSvg`, `generateStroke`, `generateInfill`, `orderPaths`, and `createFile` all take a `Settings` instance and read the fields they need directly, rather than being passed individual values. `LineType` has four draw roles (`STROKE`, `INFILL`, `GAP_INFILL`, `INVALID` - the last only emitted when `processing.showOutOfBounds` is true, see Generate above) plus `TRAVEL`, `RAW_GEOMETRY` (see Geometry Model), and three bounds-debug values.

One config file per printer, named `config/<printer>_config.json` (currently just `bambu_p1s_config.json`). Loaded via `commentjson` (supports `//` comments). `machine` (startPos/penOffset/plateSize/safeZoneSize/safeZoneOffset/canvasSize/canvasOffset — see Alignment & Scaling below), `processing` (what is drawn on paper: tessellationTolerance, penWidth, fillSpacing, prefix/suffix gcode template paths), `motion` (how the pen moves while drawing: per-role heights/speeds/accels/shortTravelThresholds, loadDelay/showLoadProgress), `visualization` (cosmetic layering/coloring for Bambu Studio preview), `debug` (showBoundingBoxes, optimizePathOrder, profiling). All fields are type-checked before use; on mismatch, the setting is skipped and a warning is printed. In `motion.heights`/`speeds`/`accels`/`shortTravelThresholds` (and `visualization.lineTypes`), a `"draw"` key sets all four draw roles at once; an explicit `stroke`/`infill`/`gapInfill`/`invalid` key overrides `"draw"` for just that role — this expansion happens once in `initFromJson`, so the rest of the pipeline just indexes by concrete `LineType`. `shortTravelThresholds` is keyed by draw move `LineType` (a travel move shorter than the threshold stays pen-down) — `plot.py`'s `_penMove` looks up the upcoming (arrival) role via `lineType or LineType.STROKE`, same fallback `heights`/`speeds`/`accels` use. When the travel follows a different-role draw move, the threshold is the min of the departing and arriving roles' values, so a short hop into (or out of) a role with a tighter threshold isn't allowed to hide behind the other role's laxer one; `_DrawState.lastLineType` tracks the most recently drawn role to make this comparison. `initFromJson` ends with `_validate()`, which calls `_validateBounds()` (warn-and-continue, never resets to defaults — see Alignment & Scaling) and also warns if `generateGapInfill` is enabled while `fillSpacing <= 0` disables fill entirely. `fillSpacing` doubles as both the infill loop pitch and the stroke pass pitch (see Stroke above).

Positions (`endPos`, `penOffset`, `plateSize`, `safeZoneSize`, `safeZoneOffset`, `canvasSize`, `canvasOffset`) are stored as `complex`, matching how positions are represented everywhere else in the codebase — JSON's 2-element lists are converted via `complex(x, y)` in `initFromJson`. `startPos` is the one exception, kept as a `dict[str, float]` (`{"X":.., "Y":.., "Z":..}`) since it needs a Z component and `createFile`'s per-file `_DrawState.pos` (current nozzle position) is built directly from it.

## Alignment & Scaling (`lib/settings.py`, `lib/svgparse.py`)

All positions/sizes below are in mm, lower-left-corner convention, and nest: **plate ⊇ safe zone ⊇ canvas**.

- `plateSize` — the heatbed rect; its lower-left corner is fixed at the origin. This is the one physical/nozzle-space rect (the bed doesn't care about the pen).
- `safeZoneSize` / `safeZoneOffset` / `safeZoneAlignment` — the rect the pen can move within without colliding with anything. `safeZoneOffset` is in **pen space** (where the pen tip should be), not gcode/nozzle space.
- `canvasSize` / `canvasOffset` / `canvasAlignment` — the paper/drawable surface, also in pen space; `canvasSize` is the field users change to resize the paper.

`safeZoneAlignment`/`canvasAlignment` (`"BL"`/`"BR"`/`"TL"`/`"TR"`, default `"BL"`) name which **plate** corner `safeZoneOffset`/`canvasOffset` is measured from: first char is Bottom/Top, second is Left/Right. The offset is the distance to translate *towards the plate's center* from that corner being coincident with the matching plate corner — e.g. `"BR"` with offset `(2, 1)` starts the rect's bottom-right corner coincident with the plate's bottom-right corner, then shifts it 2mm left and 1mm up. `"BL"` is a no-op under this scheme (shifting right/up from the origin is exactly today's lower-left-offset behavior), so it's the default and existing configs are unaffected. `Settings.initFromJson` resolves both fields into the plain lower-left-corner offset the rest of the pipeline already expects (`_alignedOffset`, called right after the settings loop, before `_validate()`) — nothing downstream of `initFromJson` (routing, bounds checks, svgparse) is alignment-aware; it only ever sees a lower-left offset from the plate origin, same as before this feature existed.

Since gcode X/Y commands the nozzle, and the pen tip sits at `nozzle + penOffset`, a pen-space position `P` corresponds to nozzle position `N = P - penOffset`. `parseSvg`'s printer-space transform (`lib/svgparse.py`) builds its translation this way: it centers the drawing on `canvasOffset + canvasSize/2` (a pen-space point) and only then subtracts `penOffset` to get the nozzle-space translation actually written to gcode.

`Settings._validateBounds()` (called at the end of `initFromJson`) warns — but does **not** alter the loaded values or fall back to defaults — if any containment in the chain doesn't hold, checked in hierarchy order:
- safe zone not fully inside the plate — `safeZoneOffset` is already pen-space (i.e. already expressed in the same physical bed-frame numbers the plate rect uses), so this is a direct compare.
- canvas not fully inside the safe zone (both already pen-space, compared directly).
- nozzle movement not fully inside the plate — the nozzle's actual gcode movement, driving the pen across the safe zone, sits at `safeZoneOffset - penOffset`. A safe zone that keeps the pen on the plate can still walk the nozzle off it, or vice versa, so both are checked.

`_Process.py` calls `promptRescale(svg, settings)` (a thin wrapper over `_promptRescale(svgWidth, svgHeight, canvasSize)`), which returns `(1, 1)` with no prompt if the SVG viewport already matches `canvasSize`; the chosen scale is then passed into `parseSvg`. Otherwise it prints both sizes and prompts for how to reconcile them: keep as-is, fit width, fit height, or stretch to fill both axes. When the canvas and viewport share an aspect ratio, fit-width/fit-height/stretch all reduce to the same scale, so the prompt collapses to just "keep as-is" vs. a single "rescale to fit" — using the same letter (`b`) as "stretch to fill both axes" in the general prompt, since they're the same operation in that case (helps muscle memory). The resulting scale is applied together with the Y-flip, canvas-centering, and `penOffset` compensation as one transform matrix per object (no separate steps).

## Hardware

**Bambu Lab P1S**: E-axis represents pen-tip distance (not filament). `M221 Sxx` (the extrusion ratio / flow rate command) does work on the P1S, but not down to 0: the firmware enforces an undocumented-until-asked minimum of 10%, and values below it are **silently discarded** rather than clamped or rejected — the extruder continues at whatever ratio was previously in effect, with no error and no indication anything was ignored (confirmed by direct observation of extruder gear rotation across a matrix of in-range and out-of-range `S` values, sent via gcode file from the SD card). This is why the multi-pass expansion originally looked like `M221` had no effect at all: the prior prefix sent `M221 S0`, which was discarded, leaving flow at the 100% default throughout. The current prefix instead sends `M221 S10` — the lowest value the firmware actually honors — genuinely reducing real extruder motion by 10x on top of `eAxisMultiplier` below. Separately, the planner throttles XY speed to keep up with the E rate *written into the gcode file* (i.e. pre-`M221`, since the firmware's speed-planning stage runs on the commanded move before the flow ratio is applied to the motor) — this is what `eAxisMultiplier` addresses, and why lowering `M221` alone (without also lowering the file's E values) doesn't relax the speed cap. `M203 E` raises are clamped/ignored, so the cap can't be lifted from gcode either. Workaround: `motion.eAxisMultiplier` (0.5 in the P1S config, default 1.0) scales every emitted E value in `plot.py`'s two E-emitting sites (G1 draws and G2/G3 arcs, both via `_eValue`), reducing the file's raw E rate so the planner's speed throttle stays off; combined with the prefix's `M221 S10`, actual extruder motion is a further 10x below that already-scaled value. Side effect of `eAxisMultiplier` is the slicer's total-filament stat scales down by the same factor (preview rendering is unaffected — it only needs E > 0, and doesn't simulate `M221` either). `_validate()` warns if the multiplier is ≤ 0, which drops E from every draw move and makes the slicer render the whole drawing as travels. `_eValue` is what makes that warning true for the whole range it covers: it collapses any non-positive multiplier to a literal 0, which `_addLine` then elides along with every other falsy arg. Multiplying straight through would only hold for exactly 0 — a *negative* multiplier yields a negative E, which is truthy and so survives the elision, writing a retraction into every single draw move instead of the dropped E the warning promises. Pen offset from nozzle via `penOffset` (applied after SVG Y-flip). Renderer clips to `[-5000, 5256]`. Cosmetic `; FEATURE:` comments drive preview coloring.

`lib/plot.py`'s `BED_EXCLUDE_AREA` is built by `_bedExcludeArea` (plate rect minus the canvas rect) for the slicer to render the drawable area. The canvas is placed per `canvasOffset` — in pen space when `showPenPos` (the slicer applies `EXTRUDER_OFFSET = penOffset`), else shifted by `-penOffset` into nozzle space. Since both rects are axis-aligned, the shape is classified directly from which of the 4 plate edges (bottom/right/top/left) the canvas fails to touch ("gap" flags), no polygon library needed: 0 gaps → nothing excluded; all 4 → a ring (`_bridgeContours` keyholes the outer plate loop to the inner canvas hole); 2 opposite gaps → two disjoint strips (also `_bridgeContours`-joined); a contiguous run of 1-3 gaps → `_perimeterWalk` traces a single simple polygon (|/L/C) directly, no seam needed. `_removeRedundantPoints` then drops collinear midpoints from all cases. `safeZone` is not part of this polygon.
